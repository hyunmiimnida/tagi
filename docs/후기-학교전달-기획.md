# 후기·별점을 모아 학교에 전달하기 — 기획 (2026-10-30)

> 이 문서는 **기획만** 담는다. 아직 코드는 바꾸지 않았다.
> 한 줄 요약: 활동이 끝난 공고에 **"참여했어요" + 별점 + 빠른 선택지 + 한 줄 의견**을 받고,
> 이것을 **개인을 알아볼 수 없는 통계와 요약**으로 만들어 학교의 프로그램 운영 부서에 학기마다 보낸다.

---

## 0. 지금 있는 것 (이 위에 쌓는다)

| 이미 있는 것 | 어디에 | 이번 기획에서 쓰는 방법 |
|---|---|---|
| 반복 프로그램 묶음 `seriesId` | `src/series.ts`, 상세 화면 "지난 공고" | 회차(공고 하나)끼리 만족도를 비교하는 뼈대 |
| 후기 댓글 `comments` (묶음 단위, 500자) | `supabase/schema.sql`, `components/Comments.tsx` | 그대로 둔다. 자유 후기·준비 팁 나눔용 |
| 글쓴이 숨긴 읽기 창 `comment_feed` | `supabase/moderation.sql` | 별점도 같은 방식(글쓴이 id를 안 보여 주는 뷰)으로 읽는다 |
| 신고 3건이면 자동 숨김 `reports`·`hidden` | `supabase/moderation.sql`, `admin.sql` | 한 줄 의견 신고에 같은 규칙을 쓴다 |
| 도배 막기 트리거 | `supabase/spam.sql`, `insert-guard.sql` | 같은 틀로 별점 도배 막기 |
| 이용 정지 `suspensions` | `supabase/admin.sql` | 정지된 사람은 별점도 못 남김 |
| 후기 선물(열쇠조각 5개, 하루 3번) | `supabase/gacha.sql`의 `reward_review_keys` | 별점 응답에도 같은 보상, **별점과 상관없이 똑같이** |
| 신분·학년 `profiles.status`·`grade` | `supabase/profile.sql` | 응답자를 **통계로만** 나눌 때 씀 |
| 관심 표시 `favorites` (로그인한 사람만 서버에 있음) | `supabase/schema.sql` | 퍼널(관심 → 참여)의 한 칸 |
| 관리자 화면 `/admin` | `components/admin/`, `supabase/admin.sql` | 여기에 "학교 리포트" 탭을 더한다 |
| 공고 정보(학교·교내 기관·주최) | `data/programs.json`, `data/archive.json` | 데이터베이스에는 공고 id만 두고, 학교·기관은 리포트를 만들 때 여기서 찾는다 |

**없는 것**: 별점, "참여했어요" 기록, 상세 화면 조회 수, 원문 버튼 클릭 수. 지금 사이트에는 방문 통계 도구가 없다.

용어 풀이
- **회차**: 공고 하나. 예) "2026 하계 해외봉사단 모집" 한 개
- **반복 프로그램(시리즈)**: 해마다 다시 열리는 같은 프로그램 회차들의 묶음 (`seriesId`)
- **RLS(행 단위 보안)**: Supabase 표에 "누가 어떤 줄을 읽고 쓸 수 있는지" 규칙을 붙이는 기능
- **뷰(view)**: 표에서 보여 줄 칸만 골라 만든 "읽기 전용 창"
- **트리거**: 표에 글이 들어갈 때 자동으로 실행되는 검사·작업
- **퍼널**: "본다 → 관심 → 신청 → 참여 → 만족" 처럼 단계마다 몇 명이 남는지 보는 깔때기 모양 통계

## 1. 무엇을 모을까

### 1-1. 받는 시점

- 회차의 **활동 기간이 끝난 뒤**(활동 기간이 없으면 모집 마감 뒤) 상세 화면에 "참여 후기 남기기" 카드가 열린다.
- 내가 관심 표시(☆)한 공고면 캘린더의 "지난 관심 공고"와 (나중에) 알림으로 "참여하셨나요?"를 한 번 물어본다.
- 활동 끝나고 **180일까지만** 받는다. 너무 오래된 기억은 정확하지 않다.

### 1-2. 받는 내용 (한 화면, 30초 안에 끝나게)

| 순서 | 항목 | 모양 | 필수? |
|---|---|---|---|
| ① | 참여 여부 | 참여했어요 / 신청했지만 선정되지 않았어요 / 신청했지만 참여하지 못했어요 | 필수 |
| ② | 별점 | ★ 1~5 (①이 "참여했어요"일 때만) | 참여했으면 필수 |
| ③ | 빠른 선택지 | 여러 개 고르기 (아래 표) | 선택 |
| ④ | 다시 참여할래요? | 네 / 아니요 / 잘 모르겠어요 | 선택 |
| ⑤ | 한 줄 의견 | 200자까지 | 선택 |

③ 빠른 선택지 — **좋은 점과 아쉬운 점을 같은 수만큼** 둔다 (칭찬만 고르게 되지 않게)

| 좋았어요 | 아쉬웠어요 |
|---|---|
| 도움이 됐어요 | 기대보다 얻은 게 적었어요 |
| 공지된 일정이 정확했어요 | 일정이 공지와 달랐어요 |
| 신청이 쉬웠어요 | 신청 과정이 복잡했어요 |
| 안내·소통이 친절했어요 | 안내가 부족했어요 |
| 혜택(장학금·수료증 등)을 잘 받았어요 | 혜택 지급이 늦거나 달랐어요 |

- ①에서 "선정되지 않았어요"를 고른 사람에게는 별점 대신 "신청 과정" 선택지만 보여 준다. 학교 입장에서는 "경쟁이 셌다"는 정보도 쓸모 있다.
- 선택지 목록은 코드가 아니라 설정 파일(예: `config/review-options.json`)에 두고, 저장할 때는 짧은 영어 코드(`helpful`, `schedule_ok`…)로 저장한다. 문구를 바꿔도 예전 응답과 이어진다.

### 1-3. 무엇에 묶이나

데이터베이스에는 **공고 id(회차)와 `seriesId`만** 적는다. 학교·교내 기관·주최는 리포트를 만들 때 `data/programs.json`·`archive.json`에서 찾는다.

| 묶는 단위 | 어디서 알아내나 | 왜 이렇게 |
|---|---|---|
| 회차 | `program_id` (저장) | 기본 단위 |
| 반복 프로그램 | `series_id` (저장, 나중에 묶음이 바뀌면 공고 데이터 쪽 값을 따른다) | 회차별 추이 |
| 학교 | 공고의 출처 학교 (`lib/data.ts`가 계산하는 학교 배지와 같은 규칙, 캠퍼스 포함) | 학교마다 리포트 |
| 교내 기관 | `config/schools.json`의 `units` 규칙 | 부서마다 나눠 전달 |
| 주최 | 공고의 `organizer`·`organizerType` | 바깥 기관 프로그램은 학교 리포트에서 따로 표시 |

- 사용자가 화면에서 학교 이름을 보내게 하면 **조작할 수 있다**. 그래서 서버에는 공고 id만 받는다.
- 공고가 합쳐져 id가 바뀌면 `aliases`(예전 id)로 새 공고에 이어 붙인다 (`public/api/moved.json`과 같은 방법).

### 1-4. 응답자 정보 — 통계로만

- 응답할 때의 **신분(재학생·휴학생·졸업생)과 학년**을 그 순간 값으로 같이 저장한다(나중에 학년이 올라가도 "그때 몇 학년이 만족했나"가 맞게).
- 응답자의 학교는 저장하지 않는다. 학교 설정은 "내가 보는 학교"일 뿐 그 학교 학생이라는 증명이 아니어서, 통계에 넣으면 오해를 부른다.
- 학년·신분별로 나눈 숫자는 **칸마다 5명 이상일 때만** 보여 주고, 아니면 "기타"로 합친다 (§3 참고).

## 2. 데이터 설계 초안

새 SQL 파일 `supabase/reviews.sql` 하나에 모은다. (moderation·spam·admin·gacha.sql을 먼저 실행한 뒤 실행)

### 2-1. 표 `program_reviews`

| 칸 | 모양 | 설명 |
|---|---|---|
| `id` | 번호 | |
| `program_id` | 글자 | 회차(공고 id) |
| `series_id` | 글자, 비어도 됨 | 반복 프로그램 묶음 |
| `user_id` | 계정 | 기본값 `auth.uid()`, 공개 안 함 |
| `participation` | `joined` / `not_selected` / `dropped` | ① 참여 여부 |
| `rating` | 1~5, 비어도 됨 | `joined`일 때만 필수 (검사 규칙으로 강제) |
| `options` | 글자 목록 | ③ 빠른 선택지 코드 (정해진 목록 안의 값만) |
| `again` | `yes` / `no` / `unsure`, 비어도 됨 | ④ |
| `note` | 200자까지, 비어도 됨 | ⑤ 한 줄 의견 |
| `status`, `grade` | 글자, 비어도 됨 | 응답 순간의 신분·학년 (`profiles`에서 트리거가 복사) |
| `had_favorite` | 참/거짓 | 응답 전에 이 공고를 관심 표시한 적 있는지 (트리거가 `favorites`에서 확인) |
| `hidden` | 참/거짓 | 신고로 숨김 |
| `flag` | 글자, 비어도 됨 | 이상치 표시(`burst`, `new_account` 등) — 숨기지는 않고 통계에서만 뺌 |
| `policy_version` | 글자 | 응답할 때 동의한 안내문 버전 (§6) |
| `created_at`, `updated_at` | 시각 | 서버 시각으로 덮어씀 (`insert-guard.sql`과 같은 방법) |

- **한 사람 한 회차 한 번**: `unique (user_id, program_id)`. 다시 쓰면 고치기(수정)가 되고, 보상은 처음 한 번만.

### 2-2. 누가 무엇을 할 수 있나 (RLS)

| 누구 | 할 수 있는 것 |
|---|---|
| 로그인 + 댓글 규칙 동의 + 정지 아님 | 자기 응답 쓰기·고치기·지우기 |
| 모든 사람 | `review_summary` 뷰(회차·묶음별 응답 수·평균·분포, **응답 3명 이상일 때만 숫자**)와 `review_notes_feed` 뷰(한 줄 의견, 글쓴이 id 없음, 숨김 제외) 읽기 |
| 본인 | `my_reviews` 뷰로 자기 응답만 |
| 관리자 | `admin_review_*` 함수(`assert_admin()` 확인)로 전체 |
| 학교 담당자 (3단계) | `school_report()` 함수로 **자기 학교 통계만** |

`program_reviews` 표 자체는 `comments`처럼 직접 읽기를 막는다(`revoke select`).

### 2-3. 도배 막기·신고 (있는 것 재사용)

- `spam.sql`과 같은 트리거: 20초 안에 또 쓰기, 하루 응답 10개 넘게, 같은 한 줄 의견 반복, 링크 2개 이상 → `spam:이유`
- `admin.sql`의 정지 확인 트리거를 그대로 붙인다 (`spam:suspended`)
- 한 줄 의견 신고: `reports`를 본뜬 `review_reports` 표 + `report_review()` 함수, **신고 3건이면 숨김**, 관리자 "댓글" 탭에 함께 보이게
- 관리자 화면에서 숨기기·문제 없음·지우기 (`admin_moderate_comment`와 같은 동작)

### 2-4. 열쇠조각 보상

- 응답이 처음 저장되면 **열쇠조각 5개**. 별점이 1점이든 5점이든, 선정되지 않았든 **같은 보상**. 칭찬만 쌓이지 않게 하는 핵심.
- 댓글 후기와 **하루 3번 한도를 함께 쓴다** (`key_ledger`의 `reason = 'review'` 그대로). 한 번에 여러 공고에 대충 별점만 찍는 걸 막는다.
- 고치기·지우고 다시 쓰기는 보상 없음 (`key_ledger`에 `detail = 'rv:공고id'`로 적어 두고 이미 있으면 안 줌).
- 화면에 "별점은 보상과 상관없어요. 솔직하게 남겨 주세요."를 적는다.

## 3. 믿을 수 있게

| 장치 | 내용 |
|---|---|
| 로그인 필수 | 비로그인 응답은 받지 않는다 (한 사람이 여러 번 못 하게) |
| 참여 자기 신고 | 참여 증명은 받지 않는다(학번·수료증 = 개인정보). 대신 "참여했어요"를 고른 사람만 별점, 리포트에 "자기 신고 기준"이라고 적는다 |
| 시간 조건 | 활동이 끝난 뒤에만 열림 (화면). 서버는 "관심 표시한 적 있는지"를 참고 칸으로 남겨 리포트에서 "관심 표시 후 응답 비율"을 같이 보여 준다 |
| 최소 응답 수 | 상세 화면 숫자: **3명 이상**. 학교 리포트 프로그램 한 줄: **5명 미만이면 보내지 않음**(이름만 "응답 부족"). 학년·신분으로 쪼갠 칸도 5명 미만이면 "기타" |
| 이상치 거르기 | 아래 표의 표시가 붙은 응답은 **통계에서 빼고**, 빠진 개수는 리포트에 적는다 |
| 사람이 확인 | 리포트를 보내기 전 운영자가 관리자 화면에서 한 번 훑어본다 |

이상치 표시(`flag`) 예

| 표시 | 조건 (처음 값, 운영하며 조정) |
|---|---|
| `new_account` | 가입 24시간 안에 쓴 응답 |
| `burst` | 한 회차에 1시간 안 응답이 평소의 5배 넘게 몰림 (몰린 응답 전체) |
| `straight` | 한 사람이 7일 안에 5개 넘는 회차에 모두 같은 점수 |
| `hidden` | 신고로 숨겨진 의견이 있는 응답 |

평균은 **응답 수·분포와 항상 같이** 보여 준다 (평균 4.5라도 2명이면 의미가 다르다).

## 4. 가공 방법

### 4-1. 숫자로 만드는 것

| 단위 | 보여 줄 숫자 |
|---|---|
| 회차 | 응답 수, 참여/미선정/중도 비율, 평균 별점, 1~5점 분포, 선택지별 비율, 재참여 의향(네 비율) |
| 반복 프로그램 | 위 숫자의 **회차별 추이**(작년 대비 올라갔나) |
| 교내 기관 | 기관 프로그램 평균, 가장 많이 나온 좋은 점/아쉬운 점 Top 3 |
| 학교 | 학기 전체 응답 수, 평균, 일정 정확도("일정이 공지와 달랐어요" 비율), 다른 학교 평균과 비교(다른 학교 이름은 안 밝힘) |

- **학기 정하는 법**: 활동 끝난 날 기준 3~8월 = 1학기, 9~2월 = 2학기.
- **우리 데이터로 덤**: "일정이 공지와 달랐어요"가 많은 출처는 우리 수집기의 날짜 추출 점검에도 쓴다.

### 4-2. 행동 지표와 묶은 퍼널

| 단계 | 지금 있나 | 새로 해야 할 일 |
|---|---|---|
| 상세 화면 조회 | 없음 | 하루 단위 숫자 세기 (아래) |
| 관심 표시 | 있음 (로그인한 사람만 `favorites`) | 체험 모드 사용자는 셀 수 없다고 리포트에 적기 |
| 원문 버튼 클릭 ("원문에서 신청하기") | 없음 | 하루 단위 숫자 세기 |
| 캘린더 내보내기(.ics) | 없음 | (선택) 같이 세기 |
| 참여했어요 | 이번에 생김 | |
| 만족(4점 이상)·재참여 의향 | 이번에 생김 | |

숫자 세기 방법 (추천): 새 표 `program_counters (program_id, day, kind, count)`에 **누가 눌렀는지 없이 숫자만** 올린다 (`bump_counter()` 함수).
- 개인정보가 아니라서 개인정보처리방침 부담이 작다.
- 같은 기기에서 같은 공고는 하루 한 번만 세게 브라우저에 기억 (대충의 중복 방지, 정확한 숫자는 아님 → 리포트에 "대략"이라고 적음).
- Vercel Analytics 같은 외부 도구는 공고별로 나누기 어렵고 무료 한도가 있어 쓰지 않는다.

리포트 예: `조회 820 → 관심 64 → 원문 클릭 210 → 참여했어요 18 → 만족 15 (재참여 의향 12)`
→ 학교는 "우리 공지가 학생에게 얼마나 닿고, 실제로 얼마나 만족했나"를 한 줄로 본다.

### 4-3. 한 줄 의견을 AI로 요약

- 대상: 학기·학교·기관별로 모은 한 줄 의견(숨김·이상치 제외, **5개 이상일 때만**).
- 엔진: 프로젝트 규칙대로 **Codex 먼저(생각 깊이 high), 막히면 Claude**. 수집기의 `src/ai.ts` 실행 방식을 재사용한 새 스크립트 `scripts/review-digest.ts` (내 컴퓨터에서만 실행).
- 보내기 전에 **개인 정보 지우기**: 전화번호·이메일·학번처럼 보이는 숫자·사람 이름 뒤 "선생님/교수님/조교님" 등을 규칙으로 가린다.
- AI에게 시키는 것: "좋았던 점 / 아쉬운 점 / 제안" 세 칸으로 **주제별로 묶고 몇 명이 비슷하게 말했는지** 세기. **원문 문장을 그대로 옮기지 말 것**, 특정 직원을 지목하는 내용은 "운영 인력 관련 의견 N건"으로만.
- 결과는 새 표 `review_digests`(학교·학기·기관·요약·상태)에 "검토 전"으로 저장 → 관리자가 관리자 화면에서 읽고 고친 뒤 "확정"해야 리포트에 들어간다.

## 5. 학교에 전달하기

### 5-1. 누구에게, 왜

| 부서 (학교마다 이름이 다름) | 왜 쓸모 있나 |
|---|---|
| 학생처·학생지원팀 (비교과 프로그램) | 만족도 조사를 따로 돌려도 응답이 적은 경우가 많다. 바깥 시선의 만족도·재참여 의향 |
| 교육혁신처·교수학습개발센터 | 비교과 성과 관리, 프로그램 개선 근거 |
| 대학일자리플러스센터·취업지원센터 | 취업 프로그램 홍보가 학생에게 닿는지(조회→클릭) |
| 창업지원단 | 창업 프로그램 참여·만족 추이 |
| RISE사업단·대학혁신지원사업단 | 사업 성과 지표·보고서에 넣을 "참여자 만족도" 보조 자료 |
| 국제처 | 해외 프로그램 신청 과정의 어려움 |

> 학교마다 공식 만족도 조사가 있으니, 우리 리포트는 **"외부 독립 채널의 보조 자료"**로 소개한다. 공식 평가를 대신한다고 말하지 않는다.

### 5-2. 1단계 — 학기별 리포트 (운영자가 직접 보냄)

- 관리자 화면에 **"학교 리포트" 탭**: 학교·학기를 고르면 인쇄용 페이지가 열린다(`/admin/report?school=yu&term=2026-2`).
- 브라우저의 "인쇄 → PDF로 저장"으로 PDF를 만든다 (따로 PDF 프로그램을 쓰지 않음, 인쇄용 CSS만).
- 리포트 순서: ① 한 장 요약(응답 수·평균·Top 좋은 점/아쉬운 점) ② 퍼널 ③ 기관별 표 ④ 프로그램별 표(5명 이상만) ⑤ AI 요약(확정본) ⑥ 방법 설명(자기 신고 기준, 최소 응답 수, 이상치 제외 수, 우리가 하지 않는 것)
- 보내는 방법: 학교 홈페이지의 부서 대표 메일로 운영자가 직접. 처음엔 **한 학교 시범**(§7 ⑤).
- 데이터를 그 학기 끝난 뒤 고정해(스냅숏) 다시 만들어도 숫자가 바뀌지 않게 `review_digests`에 같이 남긴다.

### 5-3. 2단계 — 학교 담당자 전용 화면

- 새 표 `school_staff (user_id, school_id, unit 비어도 됨, 승인 시각)`. 담당자는 학교 메일로 신청 → 운영자가 확인하고 SQL·관리자 화면에서 승인.
- `/school` 화면에서 자기 학교(또는 자기 기관) 리포트만 본다. 데이터는 `school_report()` 함수가 담당자인지 확인하고 **통계·확정 요약만** 돌려준다(한 줄 의견 원문도, 응답자 id도 주지 않음).
- 관리자 화면과 같은 방식(security definer + 확인 함수)이라 사이트에 비밀 키를 넣지 않는다.

### 5-4. 3단계 — 학교 공식 답변, 유료화 가능성

- **공식 답변**: 담당자가 반복 프로그램에 "다음 회차에는 이렇게 바꿉니다"를 남기면 상세 화면 후기 위에 "운영 부서 답변" 배지로 보인다. 학생은 "말하면 바뀐다"를 느껴 응답이 늘어난다.
- **유료화 아이디어** (지금 정하지 않음): 기본 학기 리포트는 무료로 두고, 맞춤 질문 추가·다른 학교 평균 비교·원하는 기간 리포트 등을 유료로.
- **지킬 원칙**: 돈을 내도 후기를 숨기거나 고칠 수 없다. 별점 순서·노출을 돈으로 바꾸지 않는다. 이 원칙을 이용약관에 적는다.

## 6. 개인정보·약관

> ⚠️ 아래는 운영 방향 정리이고 **법률 자문이 아니다.** 특히 "제3자 제공에 해당하는지", "통계로 만든 정보가 개인정보가 아닌지", "약관 변경 공지 기간"은 시작 전에 개인정보보호위원회 상담(국번 없이 182, 개인정보 침해신고센터)이나 전문가 확인을 받는다.

### 6-1. 기본 방향

- 학교에는 **개인을 알아볼 수 없는 통계와 요약만** 준다. 응답자 id·닉네임·한 줄 의견 원문은 주지 않는다.
- 작은 칸 위험: "○○학과 4학년 졸업생 1명"처럼 숫자가 작으면 누군지 알 수 있다 → 5명 미만 칸 숨김(§3)으로 막는다.
- 응답은 탈퇴하면 지운다. 다만 이미 확정해 보낸 리포트 숫자는 고칠 수 없다고 미리 알린다.

### 6-2. 개인정보처리방침 (`app/privacy/page.tsx`)에서 바꿀 것

| 곳 | 바꿀 내용 |
|---|---|
| 1. 모으는 정보 표 | 새 줄: "참여 후기(참여 여부·별점·선택지·한 줄 의견), 응답할 때의 신분·학년" → "다른 학생에게 프로그램 만족도 보여 주기, **개인을 알아볼 수 없는 통계·요약으로 만들어 학교 등 프로그램 운영 기관에 제공**, 서비스 개선" |
| 1. 모으는 정보 표 | (조회·클릭 숫자 세기를 하면) "공고별 조회·원문 클릭 수 — 누가 했는지 모으지 않음" 안내 한 줄 |
| 2. 보관 기간 | 후기는 탈퇴하거나 지울 때까지, 이미 만든 통계는 개인과 연결되지 않아 남는다 |
| 3. 맡기는 곳 | 의견 요약에 AI(OpenAI Codex·Anthropic Claude)를 쓰면 처리 위탁·국외 이전 표에 추가 (개인 정보를 지운 뒤 보낸다고 적기) |
| "다른 곳에 주지 않습니다" 문장 | "통계·요약 형태로 학교 등에 제공하는 경우를 빼고"로 고치기 |

### 6-3. 이용약관 (`app/terms/page.tsx`)에서 바꿀 것

- 새 조항 "참여 후기": 후기의 책임·권리는 쓴 사람에게 있고, **서비스 안 표시·통계·요약 목적으로 서비스가 이용할 수 있도록 허락**한다는 내용.
- 학교 등에는 통계·요약만 주고 원문과 글쓴이는 주지 않는다는 약속.
- 3단계를 하면: 학교 답변 표시, 돈을 받아도 후기를 숨기거나 바꾸지 않는다는 원칙.
- `lib/policy.ts`의 `POLICY_DATE`를 바꾸고, 사이트 공지(`announcements`)로 개정을 미리 알린다. 공지 기간(보통 7일, 사용자에게 불리하면 더 길게)은 확인 필요.

### 6-4. 후기 쓸 때 안내 문구 (예시)

> 남겨 주신 후기는 다른 학생들에게 프로그램 만족도로 보여요.
> 학기마다 **누가 썼는지 알 수 없는 통계와 요약**으로 만들어 프로그램을 운영한 학교 부서에 전달할 수 있어요. 이름·닉네임·글 원문은 전달하지 않아요.
> 별점은 보상과 상관없어요. 솔직하게 남겨 주세요. [자세히 보기](/privacy)

- 처음 응답할 때 한 번 보여 주고 "확인했어요"를 누르면 `policy_version`에 그 버전을 적는다.

### 6-5. 예전 댓글(`comments`)은 쓸 수 있나

- 예전 댓글은 "학교에 전달된다"는 안내 없이 쓰인 글이다. **학교 리포트의 AI 요약에는 넣지 않는 것을 추천**한다.
- 개정 공지 이후에 쓴 댓글부터, 후기 카드에 같은 안내 문구를 붙이고 리포트 요약에 넣을지 다시 정한다.
- 댓글 **개수**("이 프로그램에 후기 N개")처럼 내용 없는 숫자는 써도 부담이 작지만, 이것도 확인 대상에 넣는다.

| ⑥ 담당자 화면 | 2단계 | 새 `school_staff` 표·`school_report()`, 새 `app/school/` | |
| ⑦ 공식 답변·유료화 | 3단계 | | |

순서 이유: 약관을 먼저 정해야 ①부터 모은 응답을 떳떳하게 학교에 쓸 수 있다. ①②만으로도 학생에게 바로 쓸모가 있어 응답이 쌓이고, 쌓인 뒤에 ③이 의미가 있다. CLAUDE.md는 각 단계를 만들 때 같이 고친다.

### 운영자가 정해야 할 것

1. **약관 개정 시점**: ① 출시 전에 할지(추천), 응답을 받은 뒤 할지
2. **받는 내용**: 빠른 선택지 문구 확정, 한 줄 의견 200자가 적당한지, "선정되지 않았어요"도 받을지
3. **최소 응답 수**: 상세 3명 / 학교 리포트 5명 (추천값) 그대로 할지
4. **보상**: 별점 응답도 5개 + 댓글과 하루 3번 한도 공유 (추천) 할지, 따로 할지
5. **응답 기간**: 활동 끝나고 180일까지 (추천)
6. **조회·클릭 숫자 세기**를 할지 (퍼널을 원하면 필요)
7. **AI 요약 범위**: 예전 댓글은 빼기(추천), 한 줄 의견만 쓸지
8. **시범 학교와 받는 부서**, 메일을 누구 이름으로 보낼지
9. **법률 확인**을 어디에 받을지 (개인정보보호위원회 상담, 지인 전문가 등)
10. 3단계 **유료화를 할지**, 한다면 "돈으로 후기를 바꾸지 않는다" 원칙을 약관에 넣는 것에 동의하는지
